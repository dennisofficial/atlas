# v1 retirement — apps/api + apps/trigger + packages/db inventory

Read-only inventory of `dennisofficial/atlas` at the commit checked out in
`/atlas/workspaces/atlas/.atlas/worktrees/dennis/v1-retirement-spec`. Every path is relative to that
root. Nothing was edited.

Classes used below:
- **v1-only** — nothing on the v2 path reads it; deleting it with v1 is safe once its client is gone.
- **v2** — belongs to the v2 control plane / agent host.
- **shared** — v1 and v2 both read it today; cannot be deleted with v1.

## 0. How the two generations sit in one process

```
main.ts → createApp() → AppModule
                        ├─ ApiModule      (apps/api/src/api)   ← "the v1 app" per apps/api/AGENTS.md:156
                        │   ├─ platform/{auth,accounts,sessions,sandboxes,notifications,presence,
                        │   │             pod-leases,desktop-auth,models,usage,...}   ← v1 tree
                        │   ├─ cloud/{secrets,mcp-*,projects,skills,github,artifacts,composer-*,
                        │   │          sandbox-provisioning,sandbox-credentials,scoped-config,
                        │   │          settings,user-files,memories,stream,agent37}      ← mixed
                        │   └─ platform/control/*                    ← v2 surface (ControlPlaneModule)
                        └─ AgentModule    (apps/api/src/agent)       ← v2 runtime (host, control, runtime)
```

- The one port: `apps/api/src/api/api.module.ts:63-134`. `ControlPlaneModule` is mounted at
  `apps/api/src/api/api.module.ts:123`; the v1 tree at `:116-122`.
- v2 control plane business logic is `packages/control` (`PostgresControlStore`,
  `apps/api/src/api/platform/control/control-plane.module.ts:52-66`). It reads/writes only the `v2`
  schema (`packages/control/src/postgres/*`).
- v1 business logic is `apps/api/src/api/platform/sessions` + `apps/api/src/api/cloud/sandbox-provisioning`
  and reads `public."Thread"`, `public."Event"`, `public."CloudSandbox"`.
- Model access style everywhere: `db.orm.public.X` / `db.orm.v2.X` (`packages/db/src/client.ts:30-38`).
  `orm.public.Thread` appears 140×, `orm.public.CloudSandbox` 137×, `orm.v2.V2Session` 80×.

### 3c. Migrations

- Location `packages/db/migrations/app/<ts>_<slug>/{migration.ts,ops.json,migration.json}`; 127
  migrations, oldest `20261022T0209_baseline`. Snapshot contracts in `packages/db/migrations/snapshots/`.
  No raw `migration.sql` — each migration is a TS class over `@prisma/orm-postgres/migration`
  and its generated `ops.json` (precheck/execute/postcheck SQL), e.g.
  `migrations/app/20261122T2035_drop_user_vercel_credential/migration.ts:14-28`.
- Run in production only by the Render **pre-deploy**: `apps/api/package.json` `db:migrate:predeploy`
  → `apps/api/scripts/predeploy.mjs:7-22` → `scripts/migrate-deploy.mjs:37-46`
  (`prisma db migrate --to db`, 3 attempts, 20 s backoff) then `prisma db verify --strict`.
  Connections use `DIRECT_URL` when present (`packages/db/prisma.config.ts:4`).
- CI order (`.github/workflows/release.yml:58-134`): `api-image` (GHCR `atlas-api:<sha>`) and
  `migrate` run in parallel, `render-deploy` needs **both**, `render-live` then gates trigger.dev and
  the web. So **the migration lands while the previous build is still serving**.
- Policy is fix-forward, no down migrations (`apps/api/AGENTS.md:217`).
- Existing table drops and how they avoided downtime:
  - `20261122T2035_drop_user_vercel_credential` → `this.dropTable({schema:'public',table:'UserVercelCredential'})`
    (`migration.ts:15`). The code that read it was deleted in an **earlier** deploy:
    `d3085586866 fix(cloud): delete the tui direct vercel driver and client vercel credentials`,
    the drop shipped in `8880fc110` (2026-11-22). No old reader was left serving.
  - `20261029T0309_drop_local_pod_threads` → first a data step that deletes the rows
    (`data-steps.ts`, `ops.json` op `data.delete-local-pod-threads`), then
    `dropTable public.LocalPodCheckpoint`. Same pattern: data first, drop second.
  - `20261028T2316_drop_organizations`, `20261113T0321_drop_operator_request`,
    `20261029T2056_drop_secret_kind` — same shape, drop a table/column nothing in the current build reads.
- `subscribe`/`pub` and `pg_squeeze` maintenance: `20261124T1539_pg_squeeze_github_webhook_inbox`.

**Conclusion for v1**: dropping `public."Thread"`, `"Event"`, `"Session"`, `"SandboxBootStep"`,
`"CloudSandbox"`, `"Turn"`, `"ThreadRead"`, `"ContextFile"`, `"LocalPodLease"`, `"PushDevice"` is only
downtime-free if the build that still reads them is **already gone** when the drop migration runs —
i.e. drop in the deploy _after_ the code removal, exactly like `8880fc110`. A single deploy that both
removes the readers and drops the tables will have the old image erroring between `migrate` and
`render-live`.

## 5. Deploy

- Production is the **image-backed Render web service `atlas-api-image`** `srv-dbuu4tui0phs73ercifg`
  over PlanetScale `atlas/main`; Render builds nothing and auto-deploy is off
  (`apps/api/AGENTS.md:184-214`).
- `.github/workflows/release.yml` on every push to `main`: `api-image` builds
  `apps/api/docker/Dockerfile` (linux/amd64, `ATLAS_APP_VERSION=<sha>`) and pushes
  `ghcr.io/<owner>/atlas-api:<sha>` and `:latest`; `migrate` runs `db:migrate:predeploy`;
  `render-deploy` POSTs `{"imageUrl": …:<sha>}` to the Render API (`release.yml:120-133`);
  `render-live` waits with `apps/api/scripts/render-deploy-gate.ts`; `web-live` promotes the staged
  Vercel build; `.github/workflows/trigger-v2.yml` waits for the same live deploy.
- Image contents: `oven/bun` with only `@dltech/atlas-api` and `@dltech/atlas-daemon`, and the daemon
  bundle built (`apps/api/AGENTS.md:191`). Start: `bun run --cwd apps/api start`.
- **Removing v1 modules needs no deploy step of its own**: the next merge to `main` rebuilds the image
  and redeploys. What it does need:
  1. `packages/api-router/src/generated/server.ts` regenerated and committed, or CI's `check` job
     fails on drift (`apps/api/AGENTS.md:126-128`; pre-commit hook regenerates it).
  2. `.env.*.enc` key removals in the same PR, or `test/env-alignment.spec.ts` and the pre-commit
     `scripts/check-env-tiers.ts` fail.
  3. The **v1 trigger project stopped/handed off manually** — it no longer deploys from CI
     (`apps/api/AGENTS.md:368`). Deleting `apps/api/src/trigger` without deploying that project leaves
     `github-v1-wake-sweep` running against dropped tables.
  4. Render env itself carries only `DOTENV_PRIVATE_KEY_PRODUCTION_ENC`, `APP_TIER`, `BUN_VERSION`,
     `NODE_ENV` — so removing v1 keys is a tier-file commit, not a dashboard change.

## 7. Traps and things I could not confirm

1. **`SessionOrSandboxMiddleware` is not v1.** It authenticates v2 surfacing procedures with sandbox and
   pod tokens whose only issuers are `CloudSandbox` and `LocalPodLease`. Deleting `platform/sessions`
   and `platform/sandboxes` wholesale breaks 15+ non-v1 cloud modules at typecheck. The seam to move
   first is `apps/api/src/api/platform/sessions/session-or-sandbox.middleware.ts` +
   `apps/api/src/api/platform/sandboxes/{token-principal.ts,sandbox-principal-lookup.ts,sandbox-principal-cache.ts,sandbox-principal-revocations.ts,sandbox-register.ts}`.
   If v2 pods never present a token (I found no `@dltech/atlas-api-router` import in `packages/pods`
   or `apps/daemon`), then after v1 only the mac local pod uses `podReachable`, and the sandbox-token
   half becomes dead.
2. **The GitHub webhook controllers are one URL serving two consumers.** `handleSupplementaryEvent`
   (`packages/github`) takes `wake` (v1) and `deliveries` (v2). Removing v1 means editing that call
   site, not deleting the controller.
3. **`composerDrafts` / `composerUploads` are v1-named but v2-consumed** (TUI, mobile). They must
   survive the router purge or move to `sessions`/`sessionDrafts`.
4. **`PreviewTunnel`/`PreviewRoute` are shared**, and `platform/sandboxes/sandboxes.module.ts` exports
   both v1 `SandboxesService` and the preview wiring the v2 host imports.
5. **Trigger cleanup is manual for the v1 project.** There is no CI deploy of `proj_yvwotwceptrneuuasamk`
   any more; a scheduled task there keeps firing until someone stops it in the dashboard.
6. **Destructive migration ordering**: `migrate` completes before the new image is live, so any
   `dropTable` of a v1 table must ship in a release _after_ the build that stops reading it.
7. Unconfirmed: whether any external client (an old TUI build, an installed mac app) still calls v1
   procedures against `api.byatlas.io`. Nothing in the repo can answer that; the server-side procedure
   logs or an ingress metric would. Also unconfirmed: whether `public."GithubSubscription".threadId`
   rows still point at v1 threads in production — I did not query any database.
