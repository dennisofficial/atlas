# Agent-kind branch census for the `agent` extraction

Repository: `/atlas/workspaces/atlas`, HEAD `5203552d4a305654edbbd18c42c863a73948414c`, researched 2026-11-02. Read-only repository inspection; this report is outside the repository. `git status --short` was empty during inspection. No build or tests were run.

## Reading and classification

The intended rule is stronger than sharing `LoopTurnRunner`: every kind gets the same input, turn, dispatch, hook and assembly machinery, with differences resolved into configuration before that machinery runs. Sources: `/atlas/workspaces/atlas/docs/v2/roadmap.md` (Current state / Next), `/atlas/workspaces/atlas/docs/decisions/0019-v2-package-map.md` (agent versus pod), `/atlas/workspaces/atlas/docs/decisions/0020-v2-sub-agent-worktrees-and-peer-sessions.md` (decision 0020). Decisions 0019/0020 describe themselves as proposed. I apply 0020 as the requested target, not as proof every change has already shipped.

**Important current-source correction:** `agents/registry/child-runner.ts:63-70` ALREADY denies `subscribe` and DOES NOT deny the worktree tools. Decision 0020's Context describes an older source state. `WORKTREE_TOOL_NAMES` remains defined/exported but has no production TS caller. A generated `apps/tui/bin/atlas.map` contains the older source; it is not evidence of the current implementation and is excluded from conclusions.

Classification is the recommended destination, not an assertion the current branch is safe to move unchanged:
- **CONFIG**: resolve into explicit tools, prompt fragments, model policy, input policy, or a callback before entering the common loop. The loop must not infer a role from a name, store record, ancestry or a structural model-property probe.
- **POD**: host/crew/plugin ownership, lifecycle, storage, placement, observation or replication. It must stay outside `agent`, even when invoked synchronously by a tool or hook. “POD” here includes feature-owned host adapters, not a proposal to put every feature in the pod foundation.
- **DELETE**: the nested-teammate distinction dies under 0020, or the named helper is unused in production. This is a v2 disposition; slice 2 must preserve v1 through an outside-loop compatibility adapter.

Path cells below are repository-relative to **`/atlas/workspaces/atlas/`** (this single absolute prefix applies to every cell). Lines were verified against the actual files with numbered reads. Runtime column: **Inside** = executes during turn/retry/tool/prompt/input processing; **Outside** = construction or host lifecycle. **Inside → host** means the call is on the turn stack but its implementation belongs behind a host/feature port. An unconditional child-only construction choice is included: those forks are easy to miss with `if`-only greps.

## Construction today (short call-chain map)

### Main production session

1. `composeHarness` in `packages/harness/src/composition/compose.ts` builds shared features/container, model, prompts, tools, hook chain, pending queues and plugins. At **310-313** it creates queues with `skillExpander` and calls **`wireTurn`**.
2. **`wireTurn`** (`composition/turn-wiring.ts:73`) creates one shared **MessageIntake** through `bindIntake` (**110-121**). `bindIntake` combines shell/agent/service notices, plugin sources (including subscriptions), and operator queues (`composition/intake-binding.ts:31-37`). It also installs fallback scheduler for roster children (**40-54**).
3. `wireTurn` constructs **TurnDeps** (**140-180**): main prompt compiler, default pipeline, full tools and DI dispatcher, same hook chain, uploads, shared intake, context expansion, spend, compaction and watchdog/recovery ports. It registers deferred child dependency source (**193-233**).
4. Main chain is **ActivityTurnRunner → createTurnPolicyRunner → TitlingTurnRunner → optional TldrTurnRunner → PublishingTurnRunner → LoopTurnRunner** (`turn-wiring.ts:242-291`; `channel/publishing-turn-runner.ts:143-159`). The policy wrapper's `onOutcome`/`onCrashed` are separate driver callbacks, not automatically nested completion hooks.
5. PublishingTurnRunner creates a **new LoopTurnRunner for each say/runTurn/resume invocation** and wires per-thread chunk/tool-output/retry publication; it is not a different agent algorithm. `LoopTurnRunner.runTurn` calls **runTrackedTurn** at `loop/run-turn.ts:257-265`; common tracked-turn/step/dispatch code uses supplied dependencies.
6. `loop/build-harness.ts:69-125` **is a lower-level standalone factory, not the production composition root**. It directly creates JSONL stores, IDs, clock, AiSdkModelPort, tape/ledger, default assembly and a naked LoopTurnRunner (**114**). It supports injected tools/hooks/prompt but does not compose the full production feature/publishing/intake/wrapper stack. Extracting this factory alone would not unify production construction.

### Child (sub-agent or teammate)

1. `container/register-agents.ts:88-108` installs AgentSupervisor with lazy **childRunnerSource**, resolving **ChildRunnerDepsToken** later to break container cycles. `childRunnerSource` (`agents/registry/child-runner.ts:141-148`) caches resolved shared dependencies and calls **buildChildRunner** per request.
2. Spawn: `AgentSupervisor.spawn` → **ChildSpawner.spawn** → `spawnAdmitted` (`agents/registry/spawn-child.ts:54-114`) → **openChildThread** → add **freshChild** roster entry → **ChildSteps.take**. Teammate spawn has root-only gate at 80-83. Both are threads inside the parent's session, initially inheriting workspace/repo/execution location. First child log input is just its brief; no parent history copy (`open-child.ts:33-44`).
3. `ChildSteps.take` calls **steppedStatus** with runner factory (**child-steps.ts:109-115**); **runnerFor** (**278-292**) supplies type, child thread/cwd, progress/context/model observers and private steering accessor. **buildChildRunner** resolves placement/model, filters tools, creates child assembly/dispatcher/drain, and returns **ActivityTurnRunner → PublishingTurnRunner → same LoopTurnRunner** (`child-runner.ts:157-220`).
4. A teammate uses this SAME CHILD CONSTRUCTOR, not main `wireTurn`'s wrapper chain. It differs from an ordinary child in tool denial/listing, Main prompt label, model default exemption and completion speech policy. Ordinary sub-agents cannot recursively spawn. Teammate may spawn ordinary children; child-model selection handles that ancestry.
5. Child outputs are observed to update roster; after loop ends **ChildSteps.finish** applies shell hold / completion/report bookkeeping and produces journal/notices. Separate **NoticeWake**, **resumeChild**, and `say` producers invoke same child runner through supervisor. Shared intake already carries most input, but `ChildState.pending` steering fallback, direct log append fallback, report journal/delivery queue and separate main/child scheduler bindings remain.
6. Model distinctions are supplied as a child-specific model adapter; retry loop still discovers its `switch()` implicitly. Prompt distinctions are selected late by `ctx.agent` in fragment applicability. Those are the two most important runtime-kind leaks despite sharing LoopTurnRunner.

### Concrete unification seams for slice 2

- A single agent constructor should take resolved **model**, **tool registry/dispatcher**, **prompt fragments/pipeline**, **retry/failover policy**, **input batch provider**, **output/observation ports**, and **turn policy**. No AgentType name, spawner, teammate flag or hierarchy lookup belongs inside it.
- Intake should expose the same prepare/acknowledge/release batch semantics for every producer and the same registered driver contract for every receiver. Existing `MessageIntake` / `InputBatch` are the closest implementation seam: `intake/message-intake.ts:108-170,173-185,305-365`. Host remains responsible for mapping agent IDs to running instances and durable input ownership.
- Completion-as-report is an outside-loop output consumer/producer relationship: child output becomes parent intake input. Peer-session messages are ordinary durable session inputs, not nested-teammate journal/report special cases.
- The pod/crew feature must retain spawning, roster, thread/log storage, placement, claims, lifecycle, recovery and family cancellation. These are not reasons for the loop to know a kind. Keep v1 compatibility construction outside `packages/agent` until later slices remove 0020-marked legacy machinery; roadmap requires slice 2 to change no v1 behavior.
